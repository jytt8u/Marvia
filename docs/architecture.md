# Архитектура платформы Marvia

> Этот документ сохраняет первоначальный проект архитектуры и частично
> описывает намерения. В действующем коде связь панели и нод идёт через HTTP
> API (`internal/panel/api.go`), а отзыв отдельного устройства пока не
> реализован. Актуальные возможности и ограничения — в [README](../README.md)
> и [руководстве](guide.md). Старое имя Veil в схемах не означает отдельный продукт.

Документ отвечает на вопрос «на чём всё это держится». Он про систему целиком,
а не про протокол — протокол описан отдельно в [protocol.md](protocol.md).

---

## 0. Что мы строим и для кого

Конечный пользователь — не наш клиент. Наш клиент — **тот, кто продаёт доступ**:
владелец телеграм-бота, мелкий провайдер, админ, раздающий доступ знакомым.
Их сегодня обслуживает связка «Xray + Marzban/3x-ui + чужие клиенты», и у неё
есть вполне конкретные болячки:

| Боль продавца | Что с этим делает Veil |
|---|---|
| Ноду заблокировали, надо срочно поднимать новую | установка ноды одной командой, автоматическая ротация в подписках |
| Клиенты у всех чужие и одинаковые | свой клиент, который можно отдать под своим брендом |
| Учёт трафика приблизительный, лимиты обходятся | учёт на ноде по криптографической идентичности, а не по UUID |
| Пользователь не понимает, почему «не работает» | клиент сам меряет ноды и переключается, не спрашивая человека |
| Интеграция с ботом — самописные костыли | HTTP API и вебхуки как первоклассная часть системы |

Отсюда главный вывод: **продукт — это не протокол, а сумма «протокол +
управление + клиенты + простота установки».** Протокол — фундамент, но продают
не его.

## 1. Control plane и data plane

Система делится надвое, и это деление принципиально.

```
                        ┌──────────────────────────────┐
                        │        marvia-panel            │   control plane
                        │  пользователи, подписки,     │   один инстанс
                        │  ноды, квоты, статистика     │   свой домен
                        └───┬───────────────┬──────────┘
                            │               │
                 gRPC/mTLS  │               │  HTTP API
                            │               │
        ┌───────────────────┼──────┐        └──────────► телеграм-боты
        │                   │      │                      биллинг
        ▼                   ▼      ▼                      партнёры
   ┌─────────┐        ┌─────────┐  …
   │veil-node│        │veil-node│                       data plane
   │  VPS #1 │        │  VPS #2 │                       много, одноразовые
   └────▲────┘        └────▲────┘
        │                  │
        └────────┬─────────┘
                 │ VP1
        ┌────────┴────────┐
        │  клиенты        │  Windows / Android / Linux
        └─────────────────┘
```

**Почему именно так.** Нода — расходник. Её блокируют, изымают, она уезжает
вместе с хостером. Значит нода не должна знать ничего лишнего:

- у неё нет базы пользователей — только текущий набор ключей, который ей выдали;
- она не знает о существовании других нод;
- она не знает, кто такой пользователь: у неё есть публичный ключ и квоты к нему;
- потеряв связь с панелью, она **продолжает работать** по последнему известному
  состоянию, а не роняет всех клиентов.

Панель, наоборот, живёт долго, стоит отдельно и никогда не является точкой
входа для пользовательского трафика.

## 2. Идентичность пользователя — главное преимущество архитектуры

Это то место, где выбор Noise IK окупается.

Сервер расшифровывает первое сообщение своим приватным ключом и **получает
публичный ключ клиента как побочный результат расшифровки**. Никакого поиска,
никакого перебора.

Сравнение с тем, что есть на рынке:

| Система | Как сервер узнаёт пользователя | Цена |
|---|---|---|
| VLESS / VMess | UUID внутри запроса, сверка со списком | UUID — bearer-токен: кто его увидел, тот и пользователь |
| Shadowsocks-2022 | перебор ключей всех пользователей | O(n) на каждое соединение, на тысяче юзеров заметно |
| **Veil VP1** | одна операция X25519 при расшифровке | O(1), взаимная аутентификация |

Практические следствия для платформы:

1. **Секрет пользователя никогда не уходит в сеть.** Клиент доказывает владение
   приватным ключом, но не передаёт его. Скомпрометированная нода выдаёт список
   публичных ключей — по ним нельзя выдать себя за пользователя на другой ноде.
2. **Учёт трафика привязан к криптографической идентичности**, а не к строке из
   конфига.
3. **Отзыв ключа мгновенный и локальный**: убрать публичный ключ из набора ноды.
4. **Ротация ключей** без пересоздания пользователя: у одного аккаунта может
   быть несколько ключей (ноутбук, телефон), каждый со своей статистикой, любой
   отзывается отдельно.

Последнее — прямой ответ на вечную боль продавцов: «клиент раздал конфиг
двадцати друзьям». Здесь видно, сколько устройств у аккаунта, и каждое
отключается по отдельности.

## 3. Что живёт на ноде

`veil-node` — один бинарник без внешних зависимостей.

```
veil-node
├── слушатель :443            камуфляж + VP1
├── набор пользователей       публичный ключ → квоты
├── счётчики                  байты вверх/вниз, соединения, по ключу
├── ограничитель              объём, срок, число сессий, скорость
├── исходящие правила         куда можно ходить, куда нельзя
└── связь с панелью           получить набор, отдать статистику
```

Правила, которых нода придерживается:

- **Состояние в памяти + снапшот на диск.** Перезапуск не должен обращаться к
  панели, чтобы начать обслуживать.
- **Разрыв связи с панелью — не авария.** Нода работает по последнему набору,
  копит статистику, отдаёт при восстановлении.
- **Ничего лишнего в логах.** Нода не пишет, кто куда ходил. Изъятие сервера не
  должно выдавать пользователей. Считаем только объёмы.

  Тонкое место здесь — не строки формата, а сами ошибки сети: они несут адрес
  внутри себя, а ошибки разрешения имён — само имя. `dial tcp
  93.184.216.34:443: connect: connection refused`, записанное целиком, и есть
  запись о том, куда человек шёл. Поэтому в журнал уходит не ошибка, а её
  причина без адреса — этим занимается `why` в `cmd/marvia-node/serve.go`, и
  на неё есть тест.

  Адреса подключившихся нода держит в памяти и только ради лимита устройств;
  на диск они не попадают, а панели уходит их число, а не они сами.
- **Один порт на всех.** Никаких «пользователь = отдельный порт»: это и палево,
  и неуправляемо.

### Исходящая политика

Ноде нужен чёрный список назначений, и не из соображений морали, а чтобы её не
убил абуз-отдел хостера: SMTP (спам), порты типовых брутфорсов, локальные и
служебные подсети (SSRF во внутреннюю сеть хостера). Дефолтный набор должен
идти из коробки — иначе первая же нода уедет в бан за чужие шалости.

## 4. Что живёт в панели

`marvia-panel` — control plane. Технически это скучный CRUD, и хорошо: вся
сложность должна быть в протоколе, а не здесь.

Сущности:

```
Аккаунт продавца
 └── Пользователь (подписчик)
      ├── Ключи (устройства)     публичный ключ + метка
      ├── План                   объём, срок, лимит устройств, скорость
      └── Расход                 накопленная статистика
Нода
 ├── адрес, домены, статус, здоровье
 ├── назначенные группы пользователей
 └── статистика
```

Внешние интерфейсы:

- **API для ботов** — создать пользователя, продлить, отозвать, получить
  ссылку подписки, узнать расход. Именно на него садятся телеграм-боты.
- **Вебхуки** — «квота исчерпана», «подписка истекает», «нода упала».
- **gRPC для нод** — двусторонний стрим: панель шлёт изменения набора, нода
  шлёт статистику. mTLS, нода аутентифицируется своим сертификатом.

Важно: **у панели нет пользовательского трафика.** Её домен светится только в
момент обновления подписки. Это делает её сравнительно живучей — но и означает,
что домен подписки надо иметь запасной.

### Чего панель не хранит

Ноду теряют, а панель изымают: она стоит в юрисдикции продавца, и добраться до
неё проще, чем до сервера в чужой стране. Поэтому список того, чего в ней нет,
не менее важен, чем список того, что есть.

- **Адресов покупателей нет нигде.** Панель видит адрес при каждом обновлении
  подписки, но не записывает его — ни в базу, ни в журнал. Лимит устройств
  считает нода, у себя в памяти, и присылает панели их число, а не сами
  адреса.
- **Посуточной истории по людям нет.** В `usage_daily` лежат день, нода и
  объём — без покупателя. Раньше он там был, и панель накапливала запись «кто
  на какой ноде сидел в какой день»; ни один экран её не читал, потому что все
  они суммируют по людям. Обновление панели сворачивает накопленное и стирает
  столбец.
- **Журнала подключений нет.** «На связи» у покупателя — срез с живых нод:
  соединений сейчас, адресов за час числом и когда был в последний раз. На
  пару «покупатель, нода» одна строка, и каждый отчёт её перезаписывает;
  строк за прошлые отчёты не бывает, и тест за этим следит.
- **Что осталось и зачем.** Накопительный расход по паре «покупатель, нода» —
  без дат. Он нужен по делу: по нему считается общая квота и её разделение
  между нодами. Из него видно, что человек пользовался такой-то нодой, но не
  когда и не как часто.

Что панель хранит осознанно: метки покупателей и `external_id` — обычно
телеграм-идентификатор. Это база продавца, без неё сервиса нет; копию базы
он делает сам и отвечает за неё тоже сам.

## 5. Подписки и доставка конфигов

Самое хрупкое место всей конструкции. Нода может быть неубиваемой, но если
пользователь не может получить обновлённый список нод — сервис мёртв.

Поэтому доставка конфигов должна быть многоканальной:

1. **HTTPS-подписка** на отдельном домене (не на домене панели).
2. **Зеркала подписки** на нескольких доменах — у тебя их много, это ровно тот
   случай, когда они нужны.
3. **Отдача через телеграм-бота** — бот и так есть, и Telegram в РФ работает.
   Канал доставки, не зависящий от собственных доменов, — не роскошь.
4. **Ручной конфиг** одной строкой на крайний случай.

Формат ссылки — свой, но по структуре знакомый:

```
veil://<публичный ключ ноды>@<хост>:<порт>?sni=<домен прикрытия>&fp=chrome#<имя>
```

Подписка отдаёт список нод плюс метаданные: сроки, остаток квоты, приоритеты.
Клиент сам меряет ноды и выбирает — пользователь не должен выбирать сервер из
списка, он не знает, какой из них сейчас живой.

## 6. Клиенты — и главный риск проекта

Скажу прямо, потому что на этом умирает большинство таких проектов.

**Свой протокол означает, что ни один существующий клиент его не поддерживает.**
Ни v2rayNG, ни Hiddify, ни NekoBox, ни Streisand. Продавец, который сегодня
раздаёт ссылку в любой из них, не сможет раздать нашу. Значит клиенты придётся
написать самим — под Windows, Android, Linux, а рано или поздно и под
macOS с iOS.

Это не 10% работы, это **больше половины проекта**. И это не техническая
проблема, а продуктовая: клиент должен ставиться в два клика бабушкой, сам
переключать ноды, не разряжать телефон и не падать.

Что делает эту задачу подъёмной:

- **Одно ядро на все платформы.** Ядро на Go компилируется в библиотеку для
  Android через `gomobile` и в нативный бинарь для десктопа. Логика выбора нод,
  роутинга и учёта пишется один раз.
- **Тонкий UI поверх.** Wails на десктопе, нативный Kotlin-UI на Android.
- **iOS откладываем осознанно.** $99/год, Network Extension, ревью Apple — это
  отдельный проект, и браться за него до того, как остальное работает, нельзя.

## 6a. Двуязычная нода: путь миграции с чужих клиентов

Проблема из раздела 6 — «наш протокол не понимает ни один существующий
клиент» — решается не со стороны клиента, а со стороны ноды.

Встроить VP1 в стоковый Hiddify нельзя: он работает на ядре sing-box, а туда
новый закрытый протокол от неизвестной команды не примут. Форк чужого большого
проекта означает, что пользователю всё равно ставить другое приложение, — то
есть выигрыша нет, а поддержка форка стоит дорого.

Зато **одна нода может говорить на нескольких протоколах сразу**:

```
соединение на :443
   ├── VP1?      → наш клиент
   ├── VLESS?    → Hiddify, v2rayNG, любой стоковый клиент
   ├── Trojan?   → то же самое
   └── ничего    → настоящий сайт
```

Диспетчер для этого уже есть: `internal/rewind` плюс развилка «опознали или
отдаём сайту». Добавление ветки — сотни строк, потому что у VLESS и Trojan нет
собственной криптографии, они полагаются на TLS снаружи.

**Что это меняет для продавца.** Он переезжает на нашу панель, не трогая
текущих покупателей: у тех остаётся привычное приложение и та же ссылка.
Новым выдаёт наш клиент с VP1. Стены «всем переустановить приложение» не
возникает.

**Что это меняет для нас.** Панель приносит пользу до того, как готовы
клиентские приложения. Мы перестаём продавать протокол, которого никто не
поддерживает, и начинаем продавать управление, которое умеет всё.

**Условие, без которого затея не работает.** В России стоковые клиенты сидят
на VLESS + Reality. Наша нода с обычным TLS будет *слабее* того, что у
покупателя уже есть. Значит серверная часть Reality нужна не как улучшение
маскировки, а как условие совместимости с рынком. Хорошая новость: Reality —
транспортный слой, а не протокол. Реализуем один раз, и поверх него поедут и
VLESS для чужих клиентов, и наш VP1.

Модель данных панели это уже учитывает: у подписчика может быть несколько
наборов доступа разных видов (`vp1`, `vless`, `trojan`), связанных одним
аккаунтом с общей квотой.

## 7. Устойчивость к блокировкам как операционная задача

Протокол — только половина. Вторая половина — эксплуатация.

- **Пул IP, а не один адрес.** Заблокированный IP не отбеливается. Держим
  запас, вводим в строй по мере надобности.
- **Не жечь чистые IP до готовности камуфляжа.** Каждый спалённый адрес —
  безвозвратная потеря.
- **Ротация доменов прикрытия** — набор SNI, а не один зашитый домен. Сделано:
  нода принимает список (`-reality-sni`) и **сама сообщает его панели**, панель
  раздаёт клиентам, клиент выбирает имя на каждое соединение. Держать один и
  тот же список руками в двух местах нельзя: разойдясь, они молча ломают
  подключение. Только под REALITY: при обычном TLS и за CDN имя обязано
  совпадать с сертификатом.
- **Разные хостеры и автономные системы.** Блокировка часто идёт по AS целиком.
- **Здоровье нод меряет клиент, а не только панель.** Панель из-за границы
  видит ноду живой, когда для клиента из Иркутска она уже мертва. Клиент должен
  сообщать о недоступности, а панель — выводить ноду из подписок по географии.

## 8. Дорожная карта, пересобранная под продукт

| Этап | Что | Зачем именно сейчас |
|---|---|---|
| **M0** ✅ | протокол VP1, туннель, SOCKS5, аутентификация | фундамент |
| **M1** | камуфляж: uTLS, прикрытие настоящим сайтом, мультиплексирование | без этого продавать нечего: заблокируют за неделю |
| **M2** | многопользовательский режим на ноде: наборы ключей, квоты, учёт | превращает сервер в ноду платформы |
| **M3** | панель + API + подписки | превращает набор нод в сервис |
| **M4** | клиент Windows с TUN | первый клиент, которым можно пользоваться |
| **M5** | клиент Android | основная масса пользователей здесь |
| **M6** | установка ноды одной командой, автообновление | масштабирование на чужие руки |
| **M7** | QUIC-транспорт, паддинг, проверка против классификаторов | второе поколение антидетекта |

Порядок не случаен: **M1 идёт первым, потому что все остальные этапы бесполезны,
если трафик опознаётся.** Соблазн сделать сначала панель — сильный, панель
делать приятно и результат виден. Но панель поверх опознаваемого протокола —
это красивое управление тем, что не работает.
