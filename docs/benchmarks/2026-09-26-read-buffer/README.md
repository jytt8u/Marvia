# Дополнительные проверки VP1: буферы

26.09.2026 · Windows 10.0.26200 / amd64 · Ryzen 7 7700 · Go 1.26.6,
`GOMAXPROCS=16`. База: `e7097ab4f77af963678f0a7cc44f3aa406929252`,
уже с исправленным размером исходящих кадров. Изменение ещё не выпущено.

## Что оставлено

Чтение длины кадра использует первые два байта существующего буфера.
После проверки длины тело перезаписывает заголовок. Отдельный массив через
интерфейс `io.Reader` больше не уходит в кучу на каждый кадр.

`BenchmarkReadFrameReuse`, три запуска по 2 секунды:

| Чтение одного кадра | До | После |
|---|---:|---:|
| Медиана, нс/операцию | 153,6 | 133,7 |
| Объекты на операцию | 1 | 0 |
| Выделено байт на операцию | 2 | 0 |

Это микробенчмарк копирования из памяти, **не скорость VPN**. В TLS и Noise
остаются свои аллокации. Устранение этой одной не означает отсутствия работы
сборщика мусора или доказанного снижения расхода батареи.

[До](header-before.txt) · [После](header-after.txt). Команда:

```powershell
go test ./internal/vp1 -run '^$' -bench '^BenchmarkReadFrameReuse$' -benchmem -benchtime=2s -count=3
```

Тесты проверяют чтение по одному байту, несколько кадров в одном потоке,
короткие заголовки и тела, нулевую и превышенную длину. Существующие тесты
проверяют шифрование и приём старого полного кадра.

## Что показала передача через TLS

| Путь | До, МБ/с | После, МБ/с |
|---|---:|---:|
| VP1 + TLS | 649,8 (611,1–677,3) | 670,1 (566,7–678,4) |
| TLS | 920,2 (886,9–985,9) | 964,3 (913,5–979,1) |
| VLESS + TLS | 942,4 (829,0–974,9) | 964,3 (954,5–965,9) |
| Trojan + TLS | 952,1 (765,1–965,4) | 959,8 (893,5–969,0) |

Медианы пяти парных запусков; в скобках минимум и максимум. Диапазоны VP1
пересекаются, контроли тоже колеблются. **Прирост общей скорости не доказан.**
Ни один прогон не исключён, график README на лучшие числа не заменён.

Два бинарника собраны из одинакового `cmd/marvia-bench`; изменён только
`readFrameInto`. Команда каждого запуска: `-rounds 1 -mib 512 -echoes 1000`.
Нечётные пары: до → после; чётные: после → до. Режимы внутри запуска:
TCP → TLS → VP1 → VLESS → Trojan. `round=1` внутри файлов; номер пары в имени
`before-N.jsonl` / `after-N.jsonl`. Все 50 передач завершены, каждый байт
512 МиБ проверен; TLS везде `TLS_AES_128_GCM_SHA256`. Переводы строк приведены
к LF, значения stdout сохранены. [Сводка и SHA-256 исходника](summary.json).

Среда — обычный рабочий ПК: фоновые приложения не изолированы, частоты CPU
не закреплены. Профили и тесты не запускались параллельно итоговой серии.
В стенде нет TUN, реального интернет-маршрута или измерения батареи.

## Что отклонено

Пробный вариант объединял до четырёх зашифрованных кадров в один вызов
транспорта, увеличив буфер записи с одного до четырёх кадров. Данные
отправлялись до возврата `Write`, без таймера и ожидания следующего вызова.
Три прогона дали VP1 676,8 / 680,8 / 683,9 МБ/с — в пределах прежней серии.
Стандартный TLS продолжает вызывать сокет отдельно для каждой записи.
Вариант требовал больше памяти и усложнял обработку ошибок, поэтому удалён.
[Сырые результаты пробы](rejected-batch-trial.jsonl).

По профилю аллокаций наиболее заметны `noise.cipherChaChaPoly.func1`
и `tls.Conn.readFromUntil`. Библиотеки и криптографическая схема не изменялись.
