# VP1: проверка нарезки кадров

26 сентября 2026 · Windows 10.0.26200 / amd64 · Ryzen 7 7700 · Go 1.26.6,
`GOMAXPROCS=16`. Изменение ещё не вошло в опубликованный APK или релиз ноды.

| Путь | До, МБ/с | После, МБ/с |
|---|---:|---:|
| VP1 + TLS | **435,0** (425,1–446,6) | **678,3** (673,3–685,9) |
| TLS | 954,3 (923,0–961,8) | 974,2 (965,6–977,5) |
| VLESS + TLS | 965,3 (958,3–982,1) | 974,6 (963,4–978,1) |
| Trojan + TLS | 965,0 (726,0–971,6) | 973,1 (967,8–978,5) |

Медианы пяти прогонов; в скобках минимум и максимум, без удаления выбросов.
VP1 прибавил **55,9%**. Медиана локального echo: 31,54 → 31,03 мкс;
на таком масштабе это не основание обещать снижение задержки в интернете.

## Причина и правка

Раньше 16 382 байта полезных данных вместе с двумя заголовками и тегом Noise
занимали 16 402 байта. TLS допускает до 16 384 байт данных в одной записи:
каждый такой вызов Write создавал ещё одну короткую запись с хвостом 18 байт.
Новый отправитель ограничивает данные до 16 364 байт. Приём по-прежнему
разрешает старый максимум, Noise, ключи и добивка малых кадров не меняются.

Тест `TestBulkWritesFitTLSRecord` на старом коде упал: «кадр 16402 байт требует
лишней записи TLS». На новом проходит и проверяет расшифровку всего потока.
`TestReceiverAcceptsLegacyFullSizeFrame` отдельно проверяет старый полный кадр.

В [профиле до](profile-before.txt) преобладают вызовы ОС: `runtime.cgocall`
занимает 70,9% семплов. В полном дереве профиля путь `syscall.WSASend` занимает
67,0%. Копирование памяти — 0,6%, поэтому менять буферы без необходимости
не стали. [Профиль после](profile-after.txt) тоже сохранён. Проценты профиля
Windows не следует трактовать как точный расклад затрат процессора: они
включают атрибуцию внешних вызовов и зависят от планировщика.

## Повторение

Базовая ревизия: `3287cee3cba3fd3fbd73c3ba4a7a4d6ddb58cb2e`.
Вторая сборка отличается на пути передачи только ограничением `writePayload`.
Хеши исходников находятся в [summary.json](summary.json).

Из одной и той же версии `cmd/marvia-bench` собраны два исполняемых файла.
Каждый запуск: `-rounds 1 -mib 512 -echoes 1000`. Выполнены пять пар:
нечётные «до → после», чётные «после → до». Внутри каждого запуска порядок
TCP → TLS → VP1 → VLESS → Trojan. В файлах `before-N.jsonl` и `after-N.jsonl`
сохранены все строки stdout, включая среду запуска и время. Поле `round`
равно 1; номер парного измерения задаёт имя файла.

Для каждой версии и режима пять значений `MB_per_second` сортируются:
первое — минимум, третье — медиана, пятое — максимум. Точно так же взята
медиана пяти `echo_mean_us`. У каждого прогона проверены все 512 МиБ данных;
все TLS-режимы используют `TLS_AES_128_GCM_SHA256`.

Профили снимались **отдельно** от итоговых замеров, по 10 секунд:

```powershell
go test ./cmd/marvia-bench -run '^$' -bench 'BenchmarkProtocolTransfer/VP1' -benchtime=10s -cpuprofile vp1.cpu -o bench.test.exe
go tool pprof -top bench.test.exe vp1.cpu
```

Профильный бенчмарк передаёт по 64 МиБ за итерацию и включает установление
соединения. Его скорость нельзя подставлять вместо цифр CLI выше.

Это loopback одного ПК без TUN, интернета, эмулятора или измерения батареи.
Браузер и обычные фоновые процессы не изолированы; частоты CPU не фиксировались.
Рост на сервере Linux и на Android ещё не измерен. Полная методика стенда —
в [performance.md](../../performance.md).
