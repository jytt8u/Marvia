# API для телеграм-бота

Бота пишет продавец: у каждого своя оплата, свой язык общения с покупателем,
свои тарифы. Наше дело — чтобы на этом пути не было граблей.

Рабочий пример, который можно скопировать целиком и переделать под себя, —
[examples/tg-bot](../examples/tg-bot). В релизы он не входит и поддержкой не
покрыт: это образец, а не часть платформы.

## Ключ для бота

Боту нужен **свой ключ**, а не админский токен. Админским продавец входит в
панель; отдать его боту — значит дать право удалить всех покупателей и увести
базу с секретами vless и trojan, а при утечке отозвать его нельзя, не выкинув
из панели себя самого.

Выпускается один раз, админским токеном:

```bash
curl -X POST https://panel.example.com/api/v1/keys \
  -H "Authorization: Bearer $MARVIA_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name": "телеграм-бот", "scopes": ["users"]}'
```

В ответе `secret` вида `vk_…` — он показывается **один раз**, в базе остаётся
только хеш. Дальше все запросы бота идут с ним:

```
Authorization: Bearer vk_…
```

Права:

| Право | Что даёт |
|---|---|
| `users` | завести покупателя, продлить, отключить, удалить, выдать ссылки |
| `nodes` | добавить ноду, переименовать, выключить, удалить, пригласить новый сервер |
| `read` | только смотреть; входит в любое другое право |

**Боту хватает `users`.** Он не добавляет серверы — это делает человек.

Посмотреть выпущенные (`GET /api/v1/keys`) и отозвать (`DELETE /api/v1/keys/{id}`)
можно только админским токеном: ключ, умеющий выпускать ключи, ничем не
отличается от админского. В списке видно, когда каждым пользовались последний
раз — по этому и понятно, какой ещё живой.

Отзыв действует сразу, следующий же запрос получает `401`.

Админский токен по-прежнему работает везде: у продавца, который уже написал
бота на нём, ничего не сломается от обновления панели. Но переехать стоит.

## Продажа

```bash
curl -X POST https://panel.example.com/api/v1/users \
  -H "Authorization: Bearer $MARVIA_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
        "external_id":   "tg:584930221",
        "label":         "заказ 1043",
        "expires_at":    "30d",
        "traffic_limit": 107374182400,
        "max_ips":       3,
        "speed_limit":   12500000,
        "kinds":         ["vp1", "vless", "trojan"]
      }'
```

В ответе — готовые ссылки:

```json
{
  "created": true,
  "user": { "id": 17, "external_id": "tg:584930221", "expires_at": "..." },
  "links": {
    "account":      "marvia://…",
    "subscription": "https://panel.example.com/sub/…",
    "stock":        ["vless://…", "trojan://…"]
  }
}
```

`account` — для нашего приложения. `stock` — для тех, у кого уже стоит
v2rayNG, Hiddify или NekoBox. **Склеивать ссылки самому не надо:** одна ошибка
в параметрах — и покупатель приходит с «не работает», а разбираться будешь ты.

`speed_limit` — потолок скорости в **байтах в секунду**, 0 означает «без
ограничения». В примере 12 500 000 — это 100 Мбит/с: мегабит равен ровно
125 000 байт в секунду, так что пересчёт в обе стороны точный. Так тарифы
различаются не только гигабайтами: «100 Мбит/с» и «без ограничений»
продаются по-разному.

Потолок общий на все устройства покупателя и на все ноды разом. Считается по
трафику на проводе — по тем же байтам, что и квота, вместе с добивкой;
иначе «100 Мбит/с» на проводе давали бы заметно больше.

### external_id обязателен

Положи туда идентификатор покупателя в телеграме. Он делает две вещи.

**Позволяет найти покупателя, не держа вторую базу.** Иначе боту пришлось бы
самому помнить, какой telegram id какому номеру в панели соответствует, — а
при потере этой таблицы связь покупателей с подписками исчезнет.

**Защищает от двойной выдачи.** Платёжные системы повторяют уведомление, если
бот не ответил, а бот мог упасть ровно между вызовом панели и записью у себя.
Повторный запрос с тем же `external_id` **ничего не создаёт**: панель отвечает
успехом, возвращает существующего подписчика и ставит `"created": false`.
Новых секретов при этом не выдаёт.

То есть повтор безопасен по построению, и городить защиту в боте не нужно.

### Номер платежа — в Idempotency-Key

```
Idempotency-Key: <номер платежа>
```

Заголовок необязателен, но с ним повтор гасится **по самому платежу**, а не по
покупателю:

```bash
curl -X POST https://panel.example.com/api/v1/users \
  -H "Authorization: Bearer $MARVIA_KEY" \
  -H 'Idempotency-Key: charge_1a2b3c' \
  -d '{"external_id": "tg:584930221", "expires_at": "30d"}'
```

Повтор с тем же ключом возвращает того же подписчика, `"created": false` и
**ссылки без секретов**: доступ выдан один раз, и приватная часть в хранилище
повторов не кладётся — панель не хранит её нигде. Если бот потерял ссылку,
выдаётся новый набор доступа, а не старый.

Тот же ключ на **другого** покупателя — это не повтор, а ошибка в боте, и
панель отвечает `409`, а не молча выдаёт ответ первого.

Тот же заголовок работает и на продлении, и там он важнее всего: без него два
одновременных уведомления об одной оплате дают два месяца за одни деньги.

## Продление

```bash
curl -X PATCH https://panel.example.com/api/v1/users/17 \
  -H "Authorization: Bearer $MARVIA_KEY" \
  -d '{"extend_by": "30d"}'
```

**Не считай новый срок сам.** `extend_by` прибавляет к тому, что осталось:
покупатель, продливший за неделю до конца, эту неделю не теряет. А если
подписка давно истекла — считается от сегодня, и вернувшийся через полгода не
покупает месяц, истёкший пять месяцев назад.

Ещё важнее: продление считается одной транзакцией. Бот, который читает срок,
прибавляет месяц и записывает обратно, теряет один платёж, когда два приходят
одновременно, — и узнаёт об этом от покупателя.

Назначить срок абсолютно можно через `expires_at`, но вместе с `extend_by` он
не работает: панель откажет, а не выберет одно из двух молча.

## Найти покупателя

```bash
curl "https://panel.example.com/api/v1/users?external_id=tg:584930221" \
  -H "Authorization: Bearer $MARVIA_KEY"
```

Нет такого — `404`. Есть — список из одного.

Ответ несёт `used` (израсходовано байт), `traffic_limit`, `expires_at` и
`enabled`. Этого хватает и на «сколько у меня осталось», и на напоминание за
три дня до конца: пройди раз в сутки по `GET /api/v1/users` и отбери тех, у
кого срок близко.

Ещё три поля отвечают на «он вообще подключался?» — первый вопрос при
«не работает»: `online` — сколько соединений у него прямо сейчас,
`devices` — со скольких адресов он приходил за последний час (считается
только при заданном `max_ips`, иначе ноль), `last_seen` — когда был на связи
в последний раз, отсутствует у того, кто не подключался ни разу. Это срез с
живых нод, а не журнал: адресов, стран и истории подключений в нём нет,
и по нему нельзя ответить, где человек был вчера.

## Отключить и включить

```bash
curl -X PATCH .../api/v1/users/17 -d '{"enabled": false}'
```

Отключение действует **сразу**, в том числе на тех, кто прямо сейчас качает:
ноды проверяют это каждые пять секунд и обрывают соединения.

## Второе устройство

```bash
curl -X POST .../api/v1/users/17/credentials -d '{"kind": "vless"}'
```

Квота, срок и лимит адресов у всех наборов доступа общие — иначе достаточно
попросить второй конфиг, чтобы удвоить себе трафик. А отзывается каждый
отдельно: потерял телефон — отзови только его.

## Что бот должен переслать покупателю

1. **Ссылку `links.apps.android`** — приложение раздаёт сама панель, с домена
   продавца. Не отправляй ссылку на магазин приложений и не выкладывай apk на
   файлохостинг: и то, и другое в России отваливается первым — загрузку из
   Google Play и App Store уже ломают вместе с международными CDN.
2. **Ссылку `account`** — покупатель нажимает на неё, и приложение подхватывает
   ключ само. Вставлять руками ничего не нужно.
3. **Одну ссылку из `stock`** — на случай, если у него уже стоит v2rayNG,
   Hiddify или NekoBox.

Ссылки на приложения приходят в том же `links`, что и доступ, и только для тех
файлов, которые у продавца действительно выложены:

```json
"apps": {
  "android": "https://panel.example.com/sub/…/app/android",
  "windows": "https://panel.example.com/sub/…/app/windows"
}
```

Ключа `apps` нет вовсе — значит продавец не положил файлы в `dist` рядом с
панелью. Посмотреть, что выложено: `GET /api/v1/apps`.

Какая версия выложена, видно в `GET /api/v1/apps` — поле `version` у каждого
файла, из файла `.version` рядом с ним. Клиенты сравнивают её со своей сами
и зовут человека обновиться на домен панели; боту для этого делать ничего
не нужно.

Секреты отдаются **ровно один раз**, при выдаче. Панель приватную часть `vp1`
не хранит вовсе: утечка её базы не даёт доступа ни к одному покупателю нашего
протокола. Поэтому бот обязан переслать ссылки сразу — второй раз их взять
неоткуда, придётся выдавать новый доступ.

## Коды ответов

| Код | Что значит |
|---|---|
| `200` | получилось; смотри `created`, если это была продажа |
| `400` | панель не поняла запрос — текст в поле `error` |
| `401` | ключ не тот или отозван |
| `403` | ключу не хватает права — в ответе сказано, какого |
| `404` | нет такого покупателя |
| `500` | сломалась панель, повтори позже |

Тело ошибки всегда одинаковое: `{"error": "текст по-русски"}`.

## Ссылку подписки раздали знакомым

Так бывает чаще, чем кажется: ссылка подписки уходит в переписку или на форум,
а по ней отдаётся список нод и секреты vless с trojan.

```bash
curl -X POST .../api/v1/users/17/sub-token -H "Authorization: Bearer $MARVIA_KEY"
```

Старый адрес умирает сразу. Дальше **обязательно** выдай покупателю новый
набор доступа — в его прежней ссылке зашит путь `/sub/<старый токен>`, и
приложение по нему больше не достучится:

```bash
curl -X POST .../api/v1/users/17/credentials -d '{"kind": "vp1"}'
```

И смени утёкшие наборы: тот, кто успел прочитать старую подписку, унёс из неё
секреты, и они работают, пока живы. Смена адреса закрывает будущие чтения, а
не прошлые.

## Утёк ключ одного устройства

```bash
curl -X POST .../api/v1/credentials/42/rotate -H "Authorization: Bearer $MARVIA_KEY"
```

Набор остаётся тем же: тот же номер, та же пометка, тот же вид. Меняется
только секрет — старый перестаёт подходить, как только ноды перечитают список
(секунды). В ответе те же поля, что при выдаче нового набора, включая `links`:
оттуда берётся ссылка, которую надо отправить покупателю.

Чем это отличается от «отозвать и выдать заново». Отзыв с последующей выдачей
даёт набору новый номер и пустую пометку, а пометки у продавца осмысленные —
«телефон жены», «рабочий ноутбук». После такой замены список устройств
перестаёт читаться. Здесь же меняется ровно то, что утекло.

Вид набора смена не меняет: `vp1` остаётся `vp1`. Ключ vp1 и UUID vless —
разные вещи для приложения покупателя, и превратить одно в другое молча
значило бы сломать ему подключение без предупреждения.
