# VP1 — Veil Protocol, версия 1

Состояние: **M1b**. Криптография, камуфляж под HTTPS, мультиплексирование и
добивка кадров работают. Осталась маскировка ответа ноды (подход REALITY).
Этот документ описывает то, что реализовано, и честно перечисляет, чего не хватает.

---

## 1. Из чего состоит система

```
┌─ приложение (браузер, curl, …)
│
├─ SOCKS5 inbound          127.0.0.1:1080          ← M0
│
├─ роутинг (geoip/geosite/правила)                 ← M3, пока нет
│
├─ мультиплексор (N потоков в одном соединении)    ← M1b ✅    
│
├─ VP1: Noise IK + ChaCha20-Poly1305               ← M0 ✅
│
└─ камуфляж: uTLS + настоящий сайт для чужих       ← M1a ✅
```

Каждый слой заменяем независимо. Это не абстракция ради абстракции: слой
камуфляжа придётся менять каждый раз, когда цензор научится узнавать текущий,
а крипту при этом трогать нельзя.

---

## 2. Криптографические примитивы

| Роль | Выбор | Почему |
|---|---|---|
| Обмен ключами | X25519 | стандарт де-факто, быстрый, нет параметров, которые можно выбрать неправильно |
| Шифр | ChaCha20-Poly1305 | быстрый без аппаратного AES — важно для телефонов и дешёвых VPS |
| Хеш | BLAKE2s | требование Noise, дёшев на 32-битных платформах |
| Фреймворк | Noise Protocol Framework, паттерн `IK` | формально проанализирован, реализация `flynn/noise` |

**Своих криптопримитивов в проекте нет и не будет.** Ровно этот набор
использует WireGuard. Единственное, что мы конструируем сами, — то, как всё
это выглядит на проводе.

---

## 3. Идентичность узлов

У каждой стороны есть статическая пара ключей X25519.

- **Публичный ключ сервера** клиент обязан знать заранее (лежит в конфиге).
  Не зная его, начать разговор нельзя в принципе.
- **Публичный ключ клиента** сервер использует как идентификатор: по нему
  считается трафик, применяются лимиты и ведутся логи.

Кодирование в конфигах — base64 без паддинга (`RawURLEncoding`), 43 символа.

Генерация: `marvia-keygen`.

---

## 4. Хендшейк

Паттерн Noise **IK**: `I` — инициатор передаёт свой статический ключ,
`K` — статический ключ ответчика известен инициатору заранее.

```
клиент                                              сервер
  │                                                    │
  │  msg1 = e, es, s, ss  +  payload(время)            │
  │ ─────────────────────────────────────────────────► │  104 байта
  │                                                    │
  │            msg2 = e, ee, se  +  payload(пусто)     │
  │ ◄───────────────────────────────────────────────── │  48 байт
  │                                                    │
  │  дальше — транспортные кадры                       │
```

Каждое сообщение на проводе предваряется длиной: `uint16 big endian`.

**Prologue** — строка `veil/vp1`, подмешивается в хеш хендшейка с обеих сторон.
Не совпала — хендшейк не сойдётся. Это и есть версионирование протокола:
несовместимые версии не смогут договориться по ошибке.

**Payload msg1** — 8 байт: unix-время отправителя в наносекундах, big endian.

### Что даёт этот выбор

- Один round-trip до первого байта данных.
- Взаимная аутентификация: клиент уверен, что говорит с нужным сервером,
  сервер знает, кто к нему пришёл.
- Forward secrecy для всего трафика после хендшейка: раскрытие статических
  ключей не расшифровывает записанные ранее сессии.
- Тот, кто не знает публичный ключ сервера, не может отличить наш сервер от
  любого другого — **это фундамент защиты от active probing**, который будет
  достроен на M1.

### Чего он не даёт

Payload первого сообщения защищён слабее остальных данных: он шифруется на
статическом ключе сервера, без эфемерного вклада ответчика. Поэтому там лежит
только метка времени и никогда не будет лежать адрес назначения.

---

## 5. Защита от повтора

Noise IK сам по себе от replay не защищает: записав `msg1`, его можно послать
на сервер снова. Для цензора это инструмент — так GFW отличает прокси от
обычного сервера (сервер, реагирующий на повтор иначе, чем настоящий сайт,
выдаёт себя).

Схема — как у WireGuard:

1. Клиент кладёт в `msg1` своё время.
2. Сервер отбрасывает всё, что вне окна ±2 минуты (`ErrClockSkew`).
3. Внутри окна сервер помнит SHA-256 уже виденных `msg1` и отбрасывает
   повторы (`ErrReplay`).
4. Записи старше двух окон вычищаются, не чаще раза в секунду.

Запоминается `msg1` только от ключа из списка ноды. Разобрать `msg1` может
любой, кто знает публичный ключ ноды, — а он в каждой ссылке подписки, —
и, помни нода всех подряд, одна ссылка давала бы способ засыпать её память
свежими хендшейками с любых ключей. Повтор настоящего клиента ловится и так:
его ключ в списке. Реакция на повтор и на чужой ключ одна — сайт-прикрытие.

Следствие: **часы на клиенте и сервере должны идти верно.** Расхождение больше
двух минут — и соединение не установится. На сервере нужен работающий NTP.

## 6. Транспортные кадры и добивка

После хендшейка поток в каждую сторону состоит из кадров:

```
на проводе:
┌────────────┬─────────────────────────────────────┐
│ uint16 BE  │   ChaCha20-Poly1305(содержимое)     │
│   длина    │   = содержимое + 16 байт тега       │
└────────────┴─────────────────────────────────────┘

внутри шифра:
┌────────────┬──────────────────┬───────────────────┐
│ uint16 BE  │  полезные данные │  добивка (нули)   │
│   длина    │                  │                   │
└────────────┴──────────────────┴───────────────────┘
```

- Кадр целиком (данные + добивка + заголовок) не превышает 16384 байта —
  столько же в TLS-рекорде, и по размеру наш трафик не должен выделяться.
- Nonce ведёт `CipherState`, счётчик отдельный на каждое направление.
- Кадры обрабатываются строго по порядку — это обеспечивает TCP.
- Провал расшифровки = разрыв. Молча продолжать нельзя: либо поток изменили,
  либо счётчики разошлись.
- Кадр может целиком состоять из добивки. Получатель просто читает следующий.

### Зачем добивка

Две задачи, обе критические.

**Постоянные размеры.** Без добивки первое сообщение хендшейка всегда ровно
104 байта, второе — ровно 48. Такую пару DPI ловит правилом в одну строку, без
всякого машинного обучения. С добивкой размеры плавают в диапазонах 106…361 и
50…305.

**TLS внутри TLS.** Когда пользователь открывает HTTPS-сайт, его собственный
TLS едет внутри нашего, и размеры наших записей оказываются жёстко связаны с
размерами его записей: чужая структура просвечивает сквозь нашу оболочку.
Именно так GFW научился ловить Trojan и VLESS-over-TLS. Добивка разрывает эту
связь — сильнее всего на мелких кадрах, где структура заметнее всего.

Содержимое добивки — нули. Внутри AEAD они неотличимы от чего угодно другого,
а тратить криптографический генератор на каждый кадр незачем: случайной должна
быть длина, а не содержимое.

| Размер полезных данных | Добивка |
|---|---|
| меньше 256 байт | случайно 0…1024 |
| 256…2047 байт | случайно 0…256 |
| больше 2048 байт | нет: крупный кадр и так похож на передачу данных |

Крупный кадр при этом заполняется целиком: 16 382 байта данных плюс
заголовок — ровно TLS-рекорд во всю длину, самое обычное, что бывает в потоке
скачивания. Раньше в каждом кадре держали килобайт под добивку, которой у
крупных кадров нет: кадры выходили на килобайт короче, чем у любого HTTPS, и
их было на 7 % больше.

## 7. Мультиплексирование

Внутри одного соединения VP1 работает **yamux**: много логических потоков,
каждый со своим окном и своим полузакрытием. Окно — 4 МиБ: потолок одного
потока равен окну, делённому на RTT, и на 100 мс до Европы это 320 Мбит/с;
с прежним 1 МиБ одиночное скачивание упиралось в 80. Само шифрование не
предел: VP1 на петле даёт больше 500 МБ/с на одном ядре (`go test
./internal/vp1 -bench .`).

```
одно TCP+TLS+VP1 соединение
│
├── поток 1  →  example.com:443
├── поток 2  →  cdn.example.com:443
├── поток 3  →  api.example.com:443
└── …
```

Без этого каждое соединение браузера требовало отдельного TLS-хендшейка и
отдельного хендшейка VP1. Медленно — и, что важнее, на проводе это выглядело
как пачка одинаковых коротких соединений, вспыхивающих одновременно. Ни один
браузер так себя не ведёт.

Проверено на живом прогоне: **13 запросов пользователя прошли через одно
TCP-соединение до ноды.**

Клиент держит **пул сессий** (по умолчанию до 2 соединений, до 32 потоков в
каждом), а не одно соединение на всё. Причины две: потерянный TCP-сегмент
останавливает все потоки разом (head-of-line blocking), и единственное
соединение, тянущее весь трафик пользователя, само по себе неестественно.

Два, а не больше: несколько параллельных TLS-хендшейков к одному имени в
коротком окне — сами по себе признак, по которому ТСПУ опознаёт туннель.
По той же причине хендшейки никогда не идут одновременно, а между ними
выдерживается пауза со случайной добавкой.

### Смена сессии

Сессия живёт не дольше случайного срока в пределах **20…60 минут**. Перешагнув
его, она больше не берёт новые потоки, а опустев — закрывается; следующий поток
поднимает свежую с новым рукопожатием.

Две причины. **Forward secrecy:** эфемерный ключ Noise живёт ровно одну сессию,
и суточное соединение означало бы сутки на одном ключе — смена ограничивает то,
что вскрывается при его утечке, получасом трафика. **Картина соединений:**
браузер не держит одно TCP-соединение к сайту сутками, и туннель, открывший его
утром и не трогавший до вечера, этим и выделяется. Срок плавает, чтобы и сама
смена не стала приметой.

Активный поток при этом не рвётся никогда: уходящая сессия ждёт, пока он
договорит. Одна долгая закачка законно держит одно долгое соединение — рвать её
ради ротации значило бы чинить скрытность ценой того, ради чего всё работает.
Пул оглядывается на свои сессии сам, раз в минуту: иначе молчащий туннель
держал бы соединение до первого следующего запроса, то есть часами.

### Пинг сессии

Интервал пинга у каждой сессии свой, случайный в диапазоне 15…45 секунд.
Строго периодический пакет раз в N секунд — самостоятельный признак: обычный
трафик так не тикает, а туннели тикают. Совсем отключить пинг нельзя, иначе
NAT-трансляции протухают и сессия молча умирает.

### Полузакрытие

Тонкое место, на котором ломается большинство самодельных прокси. Когда одна
сторона договорила, ей нужно сказать «я всё сказал», не закрывая приём —
иначе ответ, который собеседник ещё не дописал, теряется. Проявляется это как
«страница загрузилась наполовину»: плавающий баг, который тяжело поймать.

В yamux `Close()` на живом потоке шлёт FIN и закрывает только исходящую
половину, но имя об этом не говорит, поэтому поток обёрнут в тип с явным
методом `CloseWrite()` (`internal/mux`). Поведение закреплено тестом
`TestHalfCloseThroughStream`.

## 8. Установка соединения через поток

Каждый логический поток начинается с запроса:

| Шаг | Кто | Что |
|---|---|---|
| 1 | клиент → нода | адрес назначения |
| 2 | нода → клиент | 1 байт статуса |
| 3 | обе стороны | сырой двунаправленный поток |

**Формат адреса** (совпадает с SOCKS5 — так его не нужно перекладывать):

```
0x01 + 4 байта      IPv4
0x03 + len + имя    домен (len — один байт)
0x04 + 16 байт      IPv6
затем uint16 BE     порт
```

**Коды статуса:** `0x00` успех, `0x01` цель недоступна, `0x02` цель запрещена,
`0x03` внутренняя ошибка, `0x04` у ноды нет пути в сеть цели.

`0x04` — это почти всегда IPv6 у ноды, которой хостер его не дал. Отдельный
код, а не «недоступна», потому что виновата нода, а не цель: клиент, получив
его, перестаёт слать IPv6 в эту сессию — на запросы AAAA отвечает сам
«адресов нет», и приложения сразу идут по IPv4. Старый клиент видит
незнакомый код и поступает с ним как с любым отказом. Старая нода отвечает
`0x01`; тогда клиент решает то же по трём IPv6-отказам подряд без единого
удачного IPv6-соединения. При переезде на другую ноду признак сбрасывается.

Домен передаётся доменом и резолвится **на ноде**. Это не мелочь: DNS-запрос,
ушедший мимо туннеля, выдаёт цензору весь список посещённых сайтов, даже когда
сам трафик он расшифровать не может.

Статус нужен, чтобы клиент не рапортовал браузеру «соединение установлено»
раньше, чем нода реально дозвонилась до цели.

## 9. Транспортный слой: камуфляж

VP1 сам по себе ничего не изображает — он даёт шифрование и подлинность.
Правдоподобие обеспечивает транспорт под ним, и он полностью заменяем.

```
клиент                                                нода :443
  │                                                        │
  │  ClientHello с отпечатком Chrome (uTLS), SNI=домен     │
  │ ──────────────────────────────────────────────────────►│
  │                        обычный TLS 1.3                 │
  │ ◄──────────────────────────────────────────────────────│
  │                                                        │
  │  внутри TLS: msg1 VP1                                  │
  │ ──────────────────────────────────────────────────────►│
  │                                                        │
  │                          ┌─────────────────────────────┴──┐
  │                          │ разобрался?                    │
  │                          │  да  → сессия и потоки         │
  │                          │  нет → отдать настоящий сайт   │
  │                          └────────────────────────────────┘
```

### Отпечаток клиента

Хендшейк выполняет **uTLS**, а не стандартный `crypto/tls`. У Go свой набор и
порядок расширений в ClientHello, то есть свой отпечаток JA3/JA4. Отпечаток,
не встречающийся у браузеров, — готовый признак для классификатора, и в Иране
по нему уже блокировали. uTLS повторяет ClientHello Chrome.

### Поведение с неопознанным гостем

Ключевая часть защиты от активного зондирования. Сканер GFW находит TLS на 443,
шлёт мусор и смотрит на реакцию. Обычный сайт отвечает страницей или ошибкой
HTTP; прокси, который молча рвёт соединение, ведёт себя иначе — и этого хватает,
чтобы IP уехал в блок-лист.

Поэтому нода записывает всё прочитанное до момента опознания
(`internal/rewind`), и если хендшейк VP1 не сошёлся — **отматывает поток назад
и отдаёт соединение обратному прокси на настоящий сайт** (`internal/fallback`).
Гость получает живую страницу с валидным сертификатом.

Сюда же попадают случаи, когда криптография сошлась, но клиент не допущен или
прислал повтор: реакция должна быть одинаковой во всех случаях, иначе разница
сама становится признаком.

### Почему шифрование двойное

Внутри TLS работает VP1, то есть данные шифруются дважды. Это осознанно:

- TLS — расходный камуфляж. Завтра вместо него будет QUIC или что-то ещё, и
  свойства безопасности от этого меняться не должны.
- Идентичность пользователя и взаимная аутентификация живут в VP1, а не в TLS.
  Скомпрометированный сертификат ноды не даёт доступа к туннелю.
- Цена — ChaCha20-Poly1305 поверх AES-GCM, порядка гигабайта в секунду на ядро.
  Для ноды на 100–1000 Мбит/с это незаметно.

## 10. Как это выглядит для DPI

| Признак | Состояние | Оценка |
|---|---|---|
| Отпечаток ClientHello | Chrome 133 через uTLS; по QUIC — Chrome 115, новее в uquic нет | **измерено**: nDPI 4.10 видит `TLS`, `Chrome`, JA4 `t13d1516h2_8daaf6152771_d8a2da3f94cd` — как у настоящего Chrome 130+. По QUIC — приемлемо |
| SNI | домен сайта-прикрытия, из набора | **измерено**: nDPI показывает SNI прикрытия, категория Web |
| Ответ на браузер | настоящий сайт, валидный сертификат | **измерено**: TLS без метки → сайт, сертификат DigiCert |
| Ответ на мусор | соединение закрывается, не висит | **измерено** |
| Ответ на повтор msg1 | тот же сайт | хорошо |
| Размеры хендшейка | плавают, 106…361 и 50…305 | хорошо |
| Размеры кадров | добивка рвёт связь с вложенным TLS | хорошо |
| Картина соединений | несколько долгоживущих, как у браузера | хорошо |
| Периодичность пинга | случайная у каждой сессии | хорошо |
| **Отпечаток ServerHello** | берётся у настоящего сайта (REALITY) | хорошо |

Дыра с отпечатком ответа закрыта на этапе M3b: под REALITY ServerHello берётся
у настоящего сайта. Остаётся вложенный TLS — он лечится добивкой, но полностью
не устраняется.

«Измерено» — стенд `scripts/stand.sh` 14 сентября 2026, Дубай → Хельсинки,
28 МБ через туннель. Единственная пометка nDPI — «Susp Extn 17613»: это ALPS,
расширение самого Chrome, которого nDPI ещё не знает; настоящий браузер
получил бы ту же. Остальные строки — по-прежнему наша оценка: JA4S и картина
соединений ждут Zeek и замера из России.

## 11. REALITY на ноде

Нода не предъявляет свой сертификат, а **проксирует TLS-хендшейк настоящему
чужому сайту**, отдавая клиенту его подлинный сертификат и его ServerHello.
Аутентификационная метка при этом прячется внутри легитимных полей
ClientHello.

Что это даёт:

- отпечаток ServerHello становится отпечатком настоящего сайта;
- собственный домен и собственный сертификат перестают быть нужны;
- SNI указывает на чужой популярный сайт, блокировать который цензор не готов;
- имя в SNI берётся из набора и меняется от соединения к соединению: одно имя
  на ноду означало бы, что блокировка домена убивает её целиком, хотя адрес
  жив. Набор задаётся на ноде флагом `-reality-sni`, нода сама сообщает его
  панели, а та раздаёт клиентам. Работает только здесь — при обычном TLS имя
  обязано совпадать с сертификатом, и выбирать не из чего;
- сканер, пришедший на ноду, получает подлинный чужой сайт, а не наш.

Реализовано на этапе M3b. Серверная часть взята готовой (github.com/xtls/reality,
форк стандартного crypto/tls): писать вместо неё собственный TLS 1.3 означало бы
нарушить главное правило проекта.

Клиентской стороны в том пакете нет: она живёт внутри Xray-core. Стоковые
приложения — v2rayNG, Hiddify — умеют REALITY сами, поэтому VLESS через нашу
ноду работает у них сразу. Наш клиент умеет её тоже — своей реализацией
(`internal/transport/reality_client.go`), которая проверяется живым
разговором с эталонным xtls/reality, а не разбором чужого кода.

## 12. Известные ограничения

- Ключ внутри сессии не меняется: смена — это новая сессия целиком, раз в
  20…60 минут (см. «Смена сессии»). Внутри этого срока ключ один.
- Потолок скорости общий на все ноды разом, а не на каждую: клиент сидит на
  одной за раз, но, подключившись к двум сразу, получил бы две доли. Поделить
  его между нодами нода не может — она не знает о существовании других.
- Нет UDP ASSOCIATE в SOCKS5: датаграммы ходят через наш протокол, но не через
  SOCKS5-клиента.
- Отпечаток ответа по QUIC — свой, а не браузерный: нода завершает
  рукопожатие стеком quic-go, а после него не говорит на HTTP/3. Пакет с
  чужой версией она не удостаивает ответом — Version Negotiation со
  списком версий нашего стека был бы готовым отпечатком, — но тому, кто
  дошёл до рукопожатия, стек виден. Под REALITY за чужой сайт прячется
  только TCP.
- Добивка стоит трафика: на мелких кадрах накладные расходы заметны.
