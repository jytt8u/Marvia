# Подготовка и переход на 0.12.0

Статус: v0.12.0 опубликован. Ниже сохранён план проверки перехода;
текущие версии приложения и серверов следует смотреть в панели и релизах.

## Что меняется

Windows больше не добавляет обходные маршруты `/32` для IP нод. Только сокеты
до нод привязываются к внешнему интерфейсу (`IP_UNICAST_IF` / `IPV6_UNICAST_IF`).
Это действует для TLS, REALITY, WebSocket, QUIC и исходящих TCP/UDP Xray,
включая Hysteria2 и WireGuard. При ошибке привязки подключение прекращается.
Интерфейс выбирается при создании каждого сокета по действующему маршруту
по умолчанию с учётом метрики интерфейса. Маршруты `/1` самого VPN не участвуют.
IPv4 и IPv6 пользовательских программ направляются в виртуальный адаптер.
Локальные сети и другие более специфичные маршруты Windows сохраняются;
это изменение не является полноценным kill switch.

Нода сохраняет рядом с файлом расхода файл `<путь-расхода>.access`. Он содержит
ключи доступа, идентификаторы аккаунтов, лимиты, сроки и последнее значение
счётчиков. Имен покупателей, адресов клиентов и истории посещений там нет.
Файл зашифрован AES-GCM ключом, полученным из токена ноды, и привязан к URL
панели. Запись атомарная, права нового файла на Linux — `0600`.
Кража и файла, и токена позволяет прочитать доступы: шифрование не заменяет
защиту сервера и секретов его службы.

При старте нода сначала обращается к панели. При недоступности разрешён
снимок не старше 24 часов; время доступа дополнительно ограничивается сроком
каждого аккаунта. Перезапуск срок не продлевает. Ответ об отключении ноды
или отозванном токене имеет приоритет и удаляет снимок. Повреждённый,
просроченный, чужой или датированный будущим снимок не принимается.
Если нет пригодного снимка, нода отказывает в старте, а не открывает доступ
всем. Счётчики из снимка и файла расхода объединяются по максимуму.
Аварийное выключение всё ещё может потерять трафик после последнего сохранения;
глобальное соблюдение квоты между изолированными нодами этим не гарантируется.

Обновлятор проверяет подпись происхождения `SHA256SUMS`, затем суммы файлов.
Разрешён только репозиторий `jytt8u/marvia`, workflow
`.github/workflows/release.yml`, выбранный тег `refs/tags/vX.Y.Z` и сборка
на GitHub-hosted runner. Приватного ключа подписи на серверах нет: workflow
получает краткоживущую подпись через GitHub OIDC / Sigstore.
Граница доверия включает сам репозиторий и его процесс сборки.

Скрипт, подпись, суммы и архив берутся из одного тега; изменение `latest`
посреди обновления их не смешивает. Установленные бинарники не исполняются
для получения версии. Копия бинарника для отката хранится во временном
каталоге root. После запуска проверяется TCP-слушатель именно у MainPID
службы. Это проверка готовности процесса, а не полноценного VPN-сеанса.

## Подготовка серверов

На каждом сервере нужны `curl`, `sha256sum`, `ss` (iproute2), systemd и
GitHub CLI с поддержкой `gh attestation verify`, `--bundle`, `--source-ref`
и `--deny-self-hosted-runners`. GitHub CLI устанавливает администратор из
доверенного источника. Обновлятор его не скачивает и не исполняет установщики.

Проверка подписи использует bundle из релиза и доверенные корни Sigstore.
Для их обновления может требоваться доступ к сети. Ноды без доступа к GitHub
по-прежнему не обновляются кнопкой: доставка через зеркало или панель в этот
этап не входит. Отсутствие подписи или инструмента проверки означает отказ,
а не переход на одни контрольные суммы.

До выкладки сохранить резервную копию базы и проверить её восстановление
в отдельном экземпляре панели. Записать текущие версии и убедиться, что
второй сервер может обслуживать клиентов во время обновления первого.

## Однократный переход после публикации тега

Сначала убедиться, что **v0.12.0 действительно опубликован** вместе с
`SHA256SUMS.sigstore.json`. Далее от root, на одном сервере:

```sh
set -eu
tag=v0.12.0
repo=jytt8u/marvia
work=$(mktemp -d)
trap 'rm -rf "$work"' EXIT
cd "$work"
base="https://github.com/$repo/releases/download/$tag"
for file in SHA256SUMS SHA256SUMS.sigstore.json upgrade.sh; do
  curl --proto '=https' --proto-redir '=https' -fsSL --max-time 120 \
    "$base/$file" -o "$file"
done
gh attestation verify SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --repo "$repo" \
  --cert-identity "https://github.com/$repo/.github/workflows/release.yml@refs/tags/$tag" \
  --source-ref "refs/tags/$tag" --deny-self-hosted-runners
grep '[ *]upgrade.sh$' SHA256SUMS | sha256sum -c -
MARVIA_RELEASE_TAG="$tag" sh ./upgrade.sh
```

Для первого перехода доверенный скрипт проверяется **до** запуска. Команду
`curl .../main/scripts/upgrade.sh | sh` для перехода больше не использовать.

После первой машины: проверить версии, журнал обновления и настоящее
подключение через её ноду. Затем повторить на второй. Массовую кнопку
для первого перехода не использовать.

Файлы приложений заменяются только при наличии их суммы в подписанном
`SHA256SUMS`. Текущий release workflow включает Windows, но не собирает APK.
Отдельно загруженный APK без подписанного манифеста не устанавливается;
на панели остаётся предыдущий файл приложения и его прежняя версия.

## Условия выпуска

- Go-тесты, vet и сборки Windows amd64, Linux amd64/arm64 проходят.
- На Windows с реальным Wintun: при открытии сайта на том же IP, что и нода,
  сайт видит выход ноды. Проверить IPv4, IPv6, UDP, переподключение и смену ноды.
- На физическом Android: Private DNS в разных режимах, настройка IPv6,
  смена Wi-Fi/мобильной сети, чужая подписка, отсутствие живого Xray после
  отключения. Эмулятор не заменяет эти проверки.
- На стенде: отключить панель, перезапустить ноду, убедиться в сохранении
  доступа и расхода; затем вернуть панель и проверить отзыв доступа.
- Выполнить обновление и вынужденный откат на Linux; проверить базу, WAL,
  пользователей и подключение клиента после отката.
- Реальная аттестация опубликованного кандидата проверяется GitHub CLI.
  Модульные тесты с подставным verifier проверяют порядок действий и отказ,
  но не заменяют эту проверку подписи.
