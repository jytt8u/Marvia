## Повторение и постоянные проверки

```sh
go install golang.org/x/vuln/cmd/govulncheck@v1.8.0
govulncheck ./...
go test ./...
go vet ./...
go test -race ./internal/vp1 ./internal/users
go test ./internal/vp1 -run '^$' -fuzz '^FuzzReadFrame$' -fuzztime=30s -parallel=2
```

Последнюю команду повторить для остальных трёх целей таблицы. Для Linux-скана
задать `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`. JSON-режим govulncheck возвращает
код 0 даже с находками: для блокирующей проверки нужен текстовый режим или
явный разбор `finding.trace`. Это учтено в [CI](../../../.github/workflows/security.yml).
Сводка содержит идентификаторы, версии, пути к уязвимым функциям и SHA-256
исходных JSON-выводов. База уязвимостей обновляется: будущие результаты могут отличаться.

Документация инструментов: [govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck),
[Go fuzzing](https://go.dev/doc/security/fuzz/).

## Как перейти к независимому аудиту

1. Зафиксировать коммит, сборки и модель угроз: сетевой посредник, кража списка
   доступа, утечка ключей TLS, захват телефона, ноды или панели.
2. Дать независимому специалисту по прикладной криптографии VP1, интеграцию
   Noise, жизненный цикл ключей/nonce, ReplayGuard, транспорты и авторизацию.
   Проверка известного шаблона Noise не равна проверке всей Marvia.
3. Отдельно проверить клиент на устройстве: DNS/IPv6, смену Wi-Fi/мобильной
   сети, разрыв туннеля, хранение ключей, экспорт журналов и обновления.
4. Получить письменный отчёт с областью проверки, версиями, воспроизводимыми
   находками и их серьёзностью; исправить и заказать повторную проверку.
5. Публиковать отчёт и статус устранения. До этого не писать «аудит пройден».
