# YouTube и имя профиля: проверка 8 октября 2026

Платформа — Windows, Яндекс Браузер; клиент на скриншоте —
Marvia 0.13.0-alpha.7. На скриншотах браузера запросы воспроизведения
к `googlevideo.com` и запросы API YouTube завершаются
`net::ERR_SSL_PROTOCOL_ERROR`. Загрузка страницы или картинки сама по себе
не подтверждает, что видео воспроизводится.

## Имя профиля Hiddify

Панель не отправляла `Profile-Title`, если у доступа не было метки или
после очистки метка становилась пустой. По
[правилам импорта Hiddify](https://github.com/hiddify/hiddify-app/wiki/URL-Scheme)
приложение тогда могло взять имя из последнего сегмента ссылки — токена
подписки. Теперь панель во всех форматах отдаёт `Marvia` для такого доступа;
заданная метка по-прежнему становится именем профиля.

`TestSubscriptionWithoutLabelHasAReadableProfileTitle` до исправления
падал на обычной подписке, `raw`, `singbox`, `clash` и `json`: заголовок
был пустым. После исправления он проходит для пустой метки, пробельных
символов и символов направления письма. Проверка непустой русской метки
также проходит. У текущего сохранённого доступа живая панель уже отдала
читаемое имя: старое имя в Hiddify требует обновления или повторного импорта
профиля. Панель на сервере в рамках этой проверки не обновлялась.

## Живые запросы через VP1

Использован сохранённый доступ компьютера, нода `fi-1`,
`89.125.41.165:443`. Ключи и токены в отчёт не включены. Соединения открыты
ядром клиента напрямую через VP1; системные маршруты не менялись.
Имена запрошены через Google DoH внутри туннеля, с тем же резолвером,
который выбран в настройках клиента.

| Проверка | Результат |
|---|---|
| DNS `www.youtube.com` | 8 адресов IPv4, 0,36 с |
| DNS `i.ytimg.com` | 7 адресов IPv4, 0,05 с |
| YouTube, HTTPS по TCP | HTTP 200, 894 195 байт, 0,31 с |
| Картинка YouTube | HTTP 200, 15 921 байт, 0,12 с |
| Google `generate_204` | HTTP 204, 0,15 с |
| API `/youtubei/v1/guide`, запрос GET | HTTP 405, 0,14 с: TLS прошёл, метод API не подходит |
| YouTube, HTTP/3 через датаграммы VP1 | HTTP 200, 795 093 байта, 0,36 с |

Это подтверждает работоспособность TCP, UDP/QUIC и DoH через выбранную
ноду на момент измерения. Эти запросы не проходили через Wintun и браузер
и не скачивали подписанный видеопоток `videoplayback`.

## Повтор через системный туннель

Во время подключения Marvia у пользователя пропадает связь с чатом.
Поэтому запущена локальная проверка, которая ждёт интерфейс Marvia и
продолжает работать без интернета для чата. В 15:06 МСК она поймала
активный интерфейс: системный MTU — 65535, системный прокси отсутствует.

Все три запроса через обычный системный маршрут — страница YouTube,
картинка и GET к API — упали с `tls: server did not echo the legacy session ID`
за 0,14, 0,11 и 0,06 с соответственно. Сразу после этого прямые запросы
через VP1 прошли: страница HTTP 200 за 0,31 с, картинка HTTP 200 за 0,13 с,
HTTP/3 HTTP 200 за 0,42 с. Отдельная проверка HTTPS по каждому IPv4-адресу
из Google DoH также прошла; разница между дозвоном по имени и по IP не
воспроизвела сбой.

На компьютере найден работающий процесс `winws` и сервис `zapret`.
zapret умеет
инъекцию TLS ClientHello с изменённым session ID, что описано в
[документации проекта](https://github.com/bol-van/zapret/blob/master/docs/readme.md).
Для проверки сервис временно остановлен с правами администратора, затем
автоматически восстановлен. При том же активном интерфейсе Marvia,
системном MTU 65535 и без системного прокси все три системных запроса
прошли: страница YouTube — HTTP 200, 892 963 байта за 0,33 с; картинка —
HTTP 200, 15 921 байт за 0,12 с; GET к API — HTTP 405 за 0,15 с.
Ошибка session ID исчезла без изменений ядра, DNS или MTU.

Это связывает воспроизведённый сбой TLS с работающим zapret. Пользователь
при первой проверке сообщил, что ошибка видео осталась; пауза сервиса
закончилась сразу после короткого измерения. Повторный сценарий должен был
держать сервис выключенным полную минуту для свежей загрузки видео, но за
пять минут не дождался адаптера Marvia и завершился без новых измерений.
Сервис остался включённым. Успешный HTTPS не выдаётся за подтверждённое
воспроизведение. Высокий
системный MTU не помешал этим HTTPS-запросам и сам по себе не объясняет
наблюдавшийся сбой.

В параметрах установленного zapret найдена обработка Google HTTPS через
`fake,multisplit` с `--dpi-desync-fooling ts` и подмена QUIC. Возможный
вариант совместимости — ограничить zapret внешним интерфейсом параметром
`--wf-iface=<индекс>`, описанным в
[документации Windows](https://github.com/bol-van/zapret/blob/master/docs/windows.md).
Тогда исходные пакеты приложений на адаптере Marvia не попадают в обработку
zapret. У этого компьютера внешний маршрут идёт через аппаратный Ethernet,
индекс 15; установленная программа содержит поддержку `--wf-iface`.
Подготовлен локальный сценарий с проверкой фильтра до изменения службы,
резервной копией параметров и откатом при ошибке запуска. Постоянные
параметры службы пока не менялись; совместная работа с таким фильтром
не проверена. При переходе на другой внешний интерфейс фильтр потребуется
обновить, поэтому это не универсальная настройка для всех компьютеров.

При отдельной проверке состояния компьютера был включён системный
HTTP-прокси `127.0.0.1:12334`. Слушающий процесс — Hiddify; активного адаптера
Marvia в этот момент не было. Через этот прокси страница YouTube отдала
HTTP 200 за 1,04 с, а тот же GET к API — HTTP 405 за 0,41 с. Наличие прокси
не доказывает обход туннеля: внешний маршрут процесса проверяется отдельно.

Чтобы воспроизвести именно путь Marvia, надо выключить соединение Hiddify,
подключить Marvia и проверить предупреждение о системном прокси на экране
«Туннель». Если остался прокси Hiddify, кнопка «Убрать прокси» снимает его.
После переключения полностью перезапустить браузер, открыть видео заново
и при повторе ошибки снять последние строки журнала Marvia. Старые
соединения и состояние проигрывателя не должны подменять эту проверку.
